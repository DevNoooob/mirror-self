# V0.2.2-M2-B：可审核记忆整合候选

开发基于 PR #10 合并后的 main `790f2f2dc3c80c05c0cacab98b67f46eefa330b6`。Mac 编辑和单元检查，GitHub Actions Java21 + 临时 PostgreSQL17/pgvector 验证；不访问 Ubuntu 业务库、不更新正式 API、不调用真实模型、不调整时钟。

## 两阶段发现

1. 显式有界扫描：每次选 1–50 条未处理或已变化的 ACTIVE / NORMAL / USER_EXPLICIT 记忆；每条关键词和现存向量各最多召回100条，经 RRF（常数60）排序，只装载前1–20个邻居。单任务最多1000次候选对比较，不做全量两两比较。
2. `ConsolidationClassifier` 检查完整命题、极性、条件/意向、类型、时间及每条 L0 用户引用。无足够证据或不能解析时弃答；相似度只负责发现，不能证明关系。跨语言复用现有证据判断器的小词汇等价表，不是通用机器翻译或 NLI。

`ConsolidationRecall` 复用现有 RetrievalRepository、pgvector、RRF、MemoryRepository 和证据结构。向量路使用数据库已有同模型/同版本/当前 revision 的1024维向量，不对记忆或查询调用 EmbeddingProvider.embed。无向量时自动仅用关键词。扫描使用模型元数据，不自动生成索引、不下载模型、不调用本地/云端模型；模型请求计数始终为0。

| 候选关系 | 产生条件 | 审核注意 |
|---|---|---|
| SAME_AS | 完整命题、极性、条件、时间一致，有相同消息时点/来源或明确同一历史年份 | 词汇等价仍需审核；不是自动合并指令 |
| SUPPORTS | 同一完整主张增加可核实来源，或另一个消息时点明确重申 | 只支持指定命题；不能证明两次消息之间始终成立 |
| CONTRADICTS | 相同时间范围内明确相反的用户表述 | 不覆盖旧记录，也不自动判定哪条是真相 |
| EVOLVED_FROM | 有日期的不同消息时点出现相反表述，或原文明确过去/消息时点变化 | 新→旧方向；仅可能演化，可能仍缺上下文 |

条件与愿望保持原承诺等级，不与完成事件混同。不同类型暂弃答，交由未来独立类型纠正流程。THOUGHT_PROCESS 仅处理已 ACTIVE 的显式自我评价，不能转为客观人格。未审核推断不参与发现。未知时间、双重否定、多事实复合句、未知改写保守弃答。显式 valid_to、superseded_by 或与消息时间不同的 valid_from 需要独立时间区间复核，当前不生成关系。

## 权限、事务与生命周期

- 所有召回、候选列表、详情、审核 SQL 限定 owner。沿用 token 与单 owner 配置，不增加跨用户入口。
- 数据库要求 ACTIVE + NORMAL + USER_EXPLICIT，至少一条证据，所有来源同 owner / PRIVATE / user，quote 仍逐字存在。RESTRICTED、SECRET、REJECTED、RETRACTED、PENDING_REVIEW 均不参与本阶段候选发现或返回。
- 候选保存 canonical UUID 对、双方 revision、关系/方向、固定原因码、不确定性、RRF排名和模型/规则版本；原文不另存快照，详情按当前授权重新加载 L0/L1。响应不携带其他关系的记忆 ID。
- 写入时按数据库 UUID 顺序锁双方 L1，再核对 revision/权限；并发、重复扫描依赖唯一约束幂等。候选唯一键不含检索设置/模型/规则版本，不能因更换模型重新开启已拒绝的相同版本关系。
- 审核需要 expectedVersion；只允许 PENDING_REVIEW → APPROVED/REJECTED，冲突返回409。APPROVED 仅批准候选关系，不写 memory_relation、不合并/删除/覆盖/重分类 L1、不更新 L2。
- 内容/类型/状态/隐私/时间/证据或 L0 元数据变化会递增 revision、使旧向量失效并把候选标记 STALE，保留此前审核记录但从常规 API 隐藏。重新满足条件时新 revision 只能产生新的待审核候选。L1 删除级联删除候选，审计仅留候选 ID；来源删除沿用既有孤立记忆清理，部分证据删除也使候选失效。
- owner+规则+模型版本+模式+邻居数形成增量游标。每个模型的索引 epoch 变化会再次扫描，避免首次无向量后的永久漏检；每种扫描设置复用游标行。索引频繁变化可能带来更多重扫，任务上限仍生效。
- 每对短事务；失败任务为 PARTIAL/FAILED，只记录固定 SCAN_UNIT_FAILED / SCAN_STORAGE_FAILED，不记录聊天或异常正文。已成功候选可幂等重试；进程强停留下 RUNNING 供诊断，尚无自动作业恢复器。

## API

新增前缀 `/api/v1/consolidation`，所有请求继续携带 `X-Mirror-Token`。不改变 `/retrieval`、`/ask` 或记忆审核契约。以下示例供未来授权的测试/部署后使用，本阶段没有操作正式 API。

```bash
# 显式扫描：KEYWORD 或 HYBRID（仅现存向量）
curl -X POST 'http://127.0.0.1:8080/api/v1/consolidation/jobs?limit=10&neighbors=10&mode=HYBRID' \
  -H "X-Mirror-Token: $MIRROR_OWNER_TOKEN"
curl 'http://127.0.0.1:8080/api/v1/consolidation/jobs/JOB_UUID' \
  -H "X-Mirror-Token: $MIRROR_OWNER_TOKEN"
curl 'http://127.0.0.1:8080/api/v1/consolidation/candidates?status=PENDING_REVIEW&limit=20&offset=0' \
  -H "X-Mirror-Token: $MIRROR_OWNER_TOKEN"
curl 'http://127.0.0.1:8080/api/v1/consolidation/candidates/CANDIDATE_UUID' \
  -H "X-Mirror-Token: $MIRROR_OWNER_TOKEN"
curl -X POST 'http://127.0.0.1:8080/api/v1/consolidation/candidates/CANDIDATE_UUID/review' \
  -H "X-Mirror-Token: $MIRROR_OWNER_TOKEN" -H 'Content-Type: application/json' \
  -d '{"decision":"APPROVE","expectedVersion":1}'
```

作业同步返回 id/status/selected/processed/comparedPairs/created/existing/abstained/stale、规则及模型版本、vectorEpoch、固定错误码和 modelRequests=0。候选双方含 id/revision/type/content/origin/status/temporalScope/occurredAt/validFrom/validTo/supersededBy、L0 sourceId/locator/quote/role/occurredAt，以及原提取版本。direction 以排序后的 memoryA/B 为基准。approvedEffect 始终为 RELATION_REVIEW_ONLY。

无 token401，非法参数/不属于 owner/失效对象400（沿用现有错误契约），已审核或版本不符409。list limit1–100，offset非负；status不填可看所有当前有效审核状态。失效候选不通过详情暴露旧正文。

## 离线质量与复现

独立虚构 `consolidation-fictional-v1.json`：31对，9个正关系，涵盖跨语言、否定、时间演化、条件目标、独立事实、人格、归因、权限和失效。参考先写入再执行；全部仍待独立人工参考复核。高风险门槛预先固定：Precision=1、Recall≥0.7、错误 SAME_AS=0、证据/审核策略正确率=1；不能用事后改答案通过测试。

## PR #11 合并前修复：资格 Top-K 与关系冲突

`consolidation-engine-2` 保持命题判断器 `consolidation-rules-1` 不变。整合专用 `RetrievalRepository.consolidationKeyword` 在 SQL WHERE 中执行完整 owner / ACTIVE / NORMAL / USER_EXPLICIT / 所有同owner PRIVATE user逐字L0证据检查，并排除anchor本身，再做排序与LIMIT。通用keyword/retrieval/ask仍使用原RetrievalVisibility，已审核推断在通用检索中的行为不变。向量路原本已执行整合资格；RRF现在只融合两路符合资格的候选，最终targets仍作防御性复核且只装载合格ID。

V4唯一键保留relation_type，用于保留不同引擎的关系假设。本次不修改该约束或任何Schema，因此不需要V5，也不编辑V4。对相同owner、规范记忆对、双方revision，存在VALID且未REJECTED的不同关系时：

- 详情及列表新增 `approvalBlocked=true`、`relationConflicts`（候选ID/关系/审核状态/引擎版本），并追加固定原因 `RELATION_TYPE_CONFLICT`。首次发现写入仅含候选ID的审计事件；不覆盖原关系、证据或审核决定。
- 新假设仍PENDING_REVIEW；双方未决时，双方APPROVE均返回409。必须显式REJECT其中一个待审假设、重新读取余下候选后再批准。已REJECTED的同版本假设不会因重扫复活。
- 若已有APPROVED，保持历史批准，新冲突假设待审且不能批准；当前接口只能拒绝新假设。改正旧批准需要未来独立授权的纠正流程，不能借升级自动撤销或覆盖。
- review与propose都先按UUID顺序锁相同L1对，序列化并发创建/审核；APPROVE SQL另用NOT EXISTS核对当前非拒绝异类假设。冲突列表仍执行owner、revision、生命周期与证据过滤；失效或被拒绝的假设不阻塞新审核。
- 如旧数据此前已有两个APPROVED关系，将显式显示冲突但不自动撤销任何审核历史，需单独人工处置；SQL直写不属于当前API的保证范围。未增加全库数据库触发器或SaaS级RLS。

扫描键包含新引擎版本，以便修复后有界重访旧游标，不更改L1 revision。没有自动启动正式扫描。
