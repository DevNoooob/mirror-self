## 2. 5/7 的实际实现问题与不可补判项

旧实现只有首轮 observer；重放只累计 accepted/inserted，没有保存 rejected、错误码、模型候选或行差异。成功条件为 `accepted>0 && inserted==0 && count/IDs unchanged`。所以空重放或全部拒绝，即便数据库完全不变，也会被历史 DUPLICATE_MEMORY 标签标记。这是已定位的指标混用问题，不是已证实的数据重复。

生产链路中 `persistValidated()` 的 extraction_fingerprint 包含 type，`MemoryRepository.save()` 的 dedupe_key 也包含 type。同一 exact 命题、证据换类型可绕开原去重。隔离测试直接运行 type-aware 存储原语可复现两行，再验证受保护服务不会重复写入。**这证明风险存在，不能倒推 MQ022/MQ032 当时一定这样发生。** 历史临时库已清理，不能补造历史重放证据。

MQ022 的3次调用仅说明重放未进入非空语义验证，仍不能区分空提取与证据全部过滤。MQ032 的4次调用说明两轮进入提取/语义阶段，仍不能区分拒绝、类型变化或实际新增。

## 3. 新增 replay-1.0 诊断，不改写旧分数

报告1.2增加独立 `replaySummary`、`replayDiagnostics`；旧1.0/1.1报告缺少这些字段时按“未记录”读取，不能默认0或通过。P/R/F1、旧 metricVersion、旧 deduplicationAccuracy/legacy重放计数全部保留；旧 Baseline 不被替换。Markdown明确旧 DUPLICATE_MEMORY 在重放语境只是复合成功判据，不是重复行证据。

每例首轮与各次重放记录：extracted、accepted、inserted、rejected、错误码、job状态、拒绝阶段；初始/前次/重放后的不透明行ID与计数；新增/移除ID，是否同集；同证据类型变化、是否同一 exact 命题；已实际观察到的 exact 重复组和具体诊断原因。报告不包含正文、quote、候选文本、provider响应、推理或内容散列。

| 指标 | 定义与限制 |
|---|---|
| modelOutputConsistency | 与首轮的候选多重集合是否相等，比较 exact内容/证据、类型、来源、敏感度和时间；忽略排列，不做语义改写等价。授权/提取失败则不纳入可比较分母，记录失败。 |
| databaseRowSetIdempotency | inserted=0 且重放后行ID集合等于首轮，与 accepted>0 无关；空输出也可稳定。包含空首轮检查。只证明观测行集合，不证明有候选真正执行了去重，也不比较所有可变属性。 |
| exactDuplicateRows | 实际数据库行中 exact内容+来源类型+时间+完整证据相同的多行；不同 MemoryType 单独显示。只算已观察事实，不以失败标签推测。 |
| typeDrifts | 同一 exact 证据出现多种 MemoryType，另标记内容/来源/时间是否也相同。共享一条来源不等于同一事实。 |

首轮持久化质量仍读取重放前快照；重放所有轮单独有诊断。跨 replay 合约版本的扩展指标不得直接当成模型提升。原正式评分不靠本次标签更名提高。

## 4. 保守的生产阻断

在已有 owner advisory lock 和事务内，证据验证通过后检查相同 exact内容、origin、temporalScope、完整来源ID与引文集合。只有全部一致且 MemoryType 不同时，抛出安全固定码 `CLASSIFICATION_CONFLICT`，原子回滚本批。

不覆盖已有类型、状态、审核结果，不复活拒绝记忆，不自动合并，不生成画像结论。既有任务查询接口可看到错误码；没有新数据库表、Schema 或 API。不同内容或独立证据的两条同源事实继续分别保存。

此规则刻意窄：不把标点、改写、不同时间或仅共享 source 的内容视为同一命题；复杂语义去重留待后续。冲突会阻断整个原子批（含同批其他新候选），需要操作者查看安全错误码后处理，不静默丢弃或改写。初次分类本身错误仍需提示/验证治理；阻断重放漂移不能自动纠正首轮分类。

## 6. 时间诊断与影响

只读原始证据见 [clock diagnostics](../evaluation/reviews/v0.2.1-c-clock-diagnostics.json)。检查时：

- Ubuntu UTC 2026-10-28T04:27:30.725480Z；Mac 请求括号约 07:29:05–07:29:08Z，宿主偏差区间为 -10897.31 到 -10894.49 秒，约慢3小时。
- Ubuntu 时区 Asia/Shanghai，但 epoch/UTC 仍与 Mac 有差；容器 UTC 04:27:31 与宿主一致。不是8小时时区转换导致。
- NTP=yes、NTPSynchronized=no；chrony active/running，tracking 显示系统慢 NTP 10896.76秒。Leap Normal/Last offset 很小不代表系统时钟已同步。
- chrony配置有 `makestep 1 3`、rtcsync：步进仅限启动前3次更新。可能与运行后大偏移难以迅速校正有关；尚无证据证明具体由VM挂起或某次人为调时引起。VMware toolbox命令不可用，不能确认其同步设置。未执行 makestep、set-time 或配置修改。
- `EvaluationJson` 直接 Instant.toString()/Instant.parse()，恒定UTC；测试在UTC/上海/纽约时区验证不发生偏移。开始时间由 Instant.now()，run目录也用UTC系统时钟；耗时另用 System.nanoTime()，不能用时区问题解释旧四小时偏差。

授权 grant 的 Java `Instant.now()+600` 与测试 PostgreSQL `now()` 同宿主时，共同固定偏差通常不会额外改变相对600秒TTL；隔离IT验证UTC往返、剩余TTL与过期拒绝。**这不证明系统绝对时间可信。** 外部调用者按可靠UTC传 expiresAt，或数据库与应用异机、运行中时钟跳变时，可能过早/过晚过期；后退时钟也可能让基于 expires_at 的过期判断再次为真，撤销条件仍独立有效。本次不弱化出站授权或自动扩大TTL。

Gold显式 statedAt/来源 occurredAt 是已有Instant，导入路径不加本机时区偏移；不会因报告时钟偏差自动加减4小时。接收/审计的 now() 时间及跨机器事件排序不可信。当前偏差约3小时而首次观测约4小时，不能假设恒定差值重写历史时间。
